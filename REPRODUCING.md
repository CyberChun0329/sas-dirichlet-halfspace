# Reproduction commands

All commands are from the repository root. Saved `runs/` evidence is
read-only input. Use a fresh destination for every experiment. No command below
invokes a full candidate-pool search.

## Identity and figures

```sh
node tools/verify_package.mjs
python3 tools/render_figures.py
```

The renderer writes only `build/rendered_figures/`. Its `--overwrite`
option applies only to that generated image set. It reads saved errors and
frontiers; it does not recompute them.

## Validation, roots and periodic histories

`make -j2 release` compiles the executables. For one isolated bank/chunk:

```sh
node tools/run_paper.mjs validation core --out build/core_new
node tools/run_paper.mjs validation case1 --out build/case1_new
node tools/run_paper.mjs validation gaussian --out build/gaussian_new
node tools/run_paper.mjs validation table_s2 --out build/s2_new
node tools/run_paper.mjs validation roots 1 --out build/roots1_new
node tools/run_paper.mjs precision --out build/precision_new
node tools/run_paper.mjs periodic unit --out build/periodic_unit_new
node tools/run_paper.mjs periodic grid 1 --out build/periodic_grid1_new
node tools/run_paper.mjs periodic invariants 1 --out build/periodic_inv1_new
```

Roots and periodic grids have chunks 1…8; invariants have cases 1…4. The runner
does not silently expand one invocation into every chunk. Different chunks may
run in separate processes, subject to available resources.

The supplementary periodic results are Tables S5–S6: temperature swings and
history/refinement checks. The validation grid has 96 depths. The refinement
subset consists of the 12 table depths and two depths at
`L=0.2, profile=Q, d=0.1`; it is specified directly in the periodic driver.

The original native aggregators expect a common `results/` directory. Copy the
new chunk outputs there without replacing a duplicate filename, then run
`summarize_validation` and `periodic_driver aggregate` from its parent. For the
saved validation set, a separate new workspace may instead receive byte copies
of `runs/correctness_01/work/results/`; remove only the copied aggregate outputs
before regenerating them. Never remove the saved source evidence.

The postprocessor interface is:

```text
build/release/stage_c_reduce RESULTS_DIRECTORY NEW_PRECREATED_OUTPUT_DIRECTORY
build/release/gaussian_coeff_check NEW_PRECREATED_OUTPUT_DIRECTORY
build/release/gaussian_original_controls NEW_PRECREATED_OUTPUT_DIRECTORY
```

The validation spatial kernel and MPFR coefficient controls are separate from
the production recurrence. They are not replaced by performance-reference floors.

## One explicit performance task

`paper_minimum/tasks.csv` is the exact 114-row paper task table, not a candidate
search specification. Its saved relative paths resolve inside this repository.
Each key file fixes the native candidate descriptors. For example:

```sh
node tools/run_paper.mjs check-timing paper_0016_N1 --out build/check_q
node tools/run_paper.mjs timing paper_0016_N1 --out build/timing_q
```

The first checks the selected saved inputs; it does not measure costs. The second
performs fresh preparation/query/total callbacks using the original formal
`paper_minimum/policy.nml`, including nine windows, the existing stopping/resource
rules and separate CPU/wall axes. It reuses same-release correctness values and
references, checks responses against them, and creates new outputs. It does not
create a fresh independent reference. Repeat counts are part of each task, not a
post hoc multiplier. Never replace one cost scope by an arithmetic reconstruction
from the other scopes.

The saved measurements used at most eight concurrent processes, with one-thread
environment settings. A new machine/load/concurrency changes timing; save that
environment and do not mix new windows into the archived paper measurements.
Concurrency is user-controlled; the runner launches one job per invocation.

The collector can reconstruct the saved full aggregate by literal
concatenation only:

```sh
node paper_minimum/collect_targets.mjs paper_minimum/tasks.csv runs/NEW_AGGREGATE
```

It requires all 114 completed output directories and refuses an existing target.
For new jobs, prepare an explicitly revised task table pointing only to their new
output directories; do not mix incomplete or old/new windows. Numerical summaries
are generated by the Fortran `replay_summary`, for example:

```sh
build/release/replay_summary runs/paper_minimum_aggregate_02/cpu_main100_comparisons.csv runs/paper_minimum_aggregate_02/cpu_main100_budgets.csv build/NEW_REPORT.md
```

## Polynomial references

Native reference files accompany the selected tasks. Optional
`make -j2 build-reference-generators` compiles the polynomial driver. Its
reference-only entry point stops after reference generation:

```text
build/release/unified_poly_driver FAMILY NEW_PRECREATED_OUTPUT_DIRECTORY config/policy.nml RELEASE_ID reference
```

`RELEASE_ID` is the scalar in `config/source_release.txt`, not a new identity for
changed sources. The polynomial families needed by saved tasks are `paper`,
`temperature_scale` and `deficit_original`; they must not be substituted for each
other. Full reference generation can be expensive. The generator exposes reference
production only. The separate `targeted_driver` performs measurements for the
explicit saved tasks.
